Research note · FlyRank ML Internship

Does a page's own numbers predict a traffic decline? A client-grouped, leakage-checked test.

Faiyaz Ifaz · github.com/FaiyazIfaz/Starter-Notebooks

Abstract Can a page's own search and engagement numbers flag which pages are likely declining, well enough to prioritize an editor's review queue? Using one month of the FlyRank ML Internship warehouse (30,000 content items across 32 clients), I built a hand-written baseline rule and a logistic regression model, validated both with a client-grouped split so no client's pages appear on both sides of training and testing. The model ranks content substantially better than random and modestly better than the hand-written rule (ROC AUC 0.66 vs 0.53), and its top 50 ranked pages are 88% in the declining group against a 54% base rate. A deliberate leakage audit found that my first feature set overlapped the label's own time window; rebuilding the features to sit strictly before that window left the result essentially unchanged, which is itself informative. This is decision-support for a review queue, not a forecast: the label is a same-month proxy, the test covers one month and 32 clients, and one client dominates the top of the ranked list in a way a human has to check before using it.

1.Introduction

An editor managing hundreds of content pages across several clients can't read every analytics row every week. They need a short list: which pages are worth a look first, and why.

FlyRank's own hand-written refresh rules (flagging a page as stale, or flagging a click-through-rate gap on page one) are a reasonable starting point, built on intuitions that other teams have used before. The question this note asks is narrow and practical: does a simple, auditable statistical model beat that hand-written rule at the one job that matters, ranking pages so the ones worth reviewing first actually come first? And can that model be trusted not to be quietly cheating, by looking at data it shouldn't have access to at decision time?

I treat this as a ranking problem with an honest proxy label, not a forecasting problem. The proxy is whether a page's impressions fell more than 20% in the most recent 30 days compared with the 30 days before that. It describes what already happened inside this snapshot, not what will happen next month.

2.Data

This work uses the FlyRank Internship Warehouse's content-refresh release, read as the month=2026-03 partition of fact_content_daily_performance, and its companion starter CSV (content_refresh_anonymized.csv), one row per content item.

What was excluded, and why

  • The sealed final month (the dataset's _sample table, June 2026) was never used to build or tune anything. It is the natural outcome window for any past-to-future label, so it is reserved as a held-out test for future work, not touched here.
  • Client and content identifiers are the warehouse's own pseudonymous hashes. No client name, URL, domain or real search query appears anywhere in this page, its notebooks, or its repository.
  • Rows with zero prior-period impressions were excluded only from the ratio-based signal check in Week 4 (division by zero), not from the model or the final ranked queue.

3.Methodology

Label

is_declining = 1 when a content item's impressions in the last 30 days of the snapshot are less than 80% of its impressions in the 30 days before that, else 0. It is a same-month proxy for "this page is slipping right now," not a forecast of a future outcome.

Baseline (hand-written rule)

A page scores 2 points if it is visible (≥500 impressions/90d), ranks on page one, and has a click-through rate at or below 0.12%; it scores 1 point if it has gone 90+ days without an update. Reason codes and a ranked queue came straight out of this rule, with no model involved.

Model and features

Logistic regression, decision tree, random forest and gradient boosting were compared on the same 18 numeric and 3 categorical features (search volume, competition, word count, 90-day performance totals, CTR, position, content age, days since update, content type, main intent). A leakage guard asserted that no label-derived or label-sibling column (trend_direction, trend_pct, any *_last_30d / *_prev_30d column) was ever in the feature list.

Validation design

5-fold cross-validation, grouped by client, so every client's pages sit entirely on one side of each fold. An assertion checked this on every fold. The hand-written rule was scored on the exact same test folds, so model and baseline are never compared on different data.

Leakage audit

A deliberate audit (detailed in Results) found that the *_90d performance columns used in the first model contain the two 30-day windows the label is built from, which fails a strict "features knowable before the label window closes" test. A second feature set was rebuilt using only the one 30-day block that sits entirely before both label windows, and a synthetic leak column (built directly from the label's own windows) was added and removed as a sanity check that the audit itself could detect a real leak.

Logistic regression was chosen over the stronger-AUC ensembles: its precision at the top of the list is the best of the model family, its gap to gradient boosting (+0.019 AUC) is within the fold-to-fold noise (std ≈0.03–0.04), and it stays fully readable. Added complexity did not buy a result worth its cost here.

The split matters more than the model

Under a naive split, Random Forest and Gradient Boosting look like the clear winners (AUC 0.76-0.77). Under the honest, client-grouped split, that gap nearly disappears (0.668-0.677), and the ordering among models barely changes. The naive split was flattering every model by letting them partly learn which client a row belonged to, rather than learning a transferable pattern.

The leakage audit's most important finding
Every *_90d feature used above technically overlaps the label's own 30-day windows, so it fails a strict leakage test. A synthetic column built directly from the label's windows confirmed the audit works (it pushed AUC from 0.658 to 0.716). But when I rebuilt the features using only the one 30-day block that sits entirely before the label window, the honest model scored 0.660, essentially unchanged. The overlap was not secretly propping up the result; the signal mostly lives in a CTR-like pattern visible even a month earlier. I report this as a negative finding, not a hidden fix, because it's informative either way.

How concentrated is the signal?

Where the model leans, and where it's wrong

By permutation importance, the model leans most on 90-day impressions and clicks (more impressions with few clicks reads as a CTR gap), then on content length and intent. Its biggest error source is the client, not any individual page: observed declining rates range from 0% to 94% across clients, something no page-level feature can see. Three concrete misses were all large, page-one, near-zero-CTR pages that stayed stable instead of declining, each one otherwise indistinguishable from a true positive on paper.

5.Limitations & honest framing

  • One snapshot month, 32 clients. Every number on this page describes March 2026 for these clients. Nothing here has been checked against a different month or an unseen client at scale.
  • The label is a proxy, not an outcome. "Declining" means impressions fell within this one 90-day window, measured by comparing two halves of the same snapshot. It is not a verified business outcome and has not been checked against the sealed final month.
  • One client dominates the ranked list. In the full-dataset ranking, a single client supplies 78% of the top 100 rows. That is expected given how the risk score is computed, but it means the queue, as built, is not yet safe to hand to a different client without re-checking it for that client alone.
  • No causal claim. This is cross-sectional data. A page having a low CTR is associated with being in the declining group; nothing here tests whether fixing the CTR would reverse the decline.
  • Modest effect size. AUC 0.66 is a real, measured improvement over both random guessing and the hand-written rule, not a dramatic one. The honest claim is decision-support for ordering a review queue, not a confident forecast.

Intended use

A content editor or SEO lead deciding which pages to look at first in a weekly or monthly review cycle. Not a page-by-page verdict, and not a tool that decides what to publish.

Human review, every time

Before anyone acts on a row: confirm the reason code against the live page, check whether the page's topic is still relevant to the business, and weigh search volume against editor time. High-volume ctr_gap_and_stale pages are worth an hour; low-volume other pages usually are not.

What should NOT be automated

  • Auto-publishing any rewritten title, meta description, or content change
  • Auto-deprioritizing or hiding pages scored fresh or other — that's "no evidence to act," not "confirmed healthy"
  • Treating the queue's row order as a guarantee rather than a useful grouping in blocks of fifty or a hundred
  • Running this unreviewed on a client it has not been checked against — re-run the reason-code table for that client alone first

Monitoring & retrain triggers

Weekly: do the five reason-code bucket sizes still look like 62% / 21% / 7% / 6% / 4%? Does one client still supply more than half of the top 100 (78% in this run)? Monthly: re-score last month's top 100 against this month's actual outcome. Retrain if: top-100 observed decline rate falls below 70% for two months running, a client's page mix changes materially, the warehouse's time-window columns change definition, or a full quarter passes untested.
